## Test 7 — Composability + A2A assessment

- MCP and AIRC are composable as orchestration primitives: MCP provides transport-neutral tool invocation, while AIRC provides identity/presence and lightweight messaging.
- In practice, AIRC is best treated as a transport substrate for trust bootstrap and discovery. MCP handles local tool-call lifecycle, session capability exchange, and tool metadata.
- If you use both, keep one source of truth for identity and authorization. AIRC identity/signature fields should be preserved in MCP payloads rather than remapped.
- A2A has explicit task lifecycle semantics (task states, artifacts, push notifications). AIRC does not define that model; it only defines how agents identify themselves, publish presence, and exchange messages.
- A realistic composition pattern is: MCP tool calls drive local agent execution; AIRC carries identity and cross-agent route metadata (who/where/consent/security). The boundary is clear, but you must implement adapters for task semantics and consent/ownership mapping.
- Overlap exists in messaging and handoff concepts, but contracts diverge: AIRC is protocol-level discovery; A2A is application-level workflow orchestration.
- Conflict is low at protocol layer, higher at implementation: duplicate retry/ack/conflict-resolution assumptions can cause inconsistent behavior without an explicit bridge contract.
- Final position: composition is accurate when framed as layered systems (MCP tool runtime + AIRC control plane), not as direct protocol substitution.
